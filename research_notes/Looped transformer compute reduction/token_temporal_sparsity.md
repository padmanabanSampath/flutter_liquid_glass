# Fewer tokens per pass: token, spatial and temporal sparsity for looped (weight-shared) transformers

Source-type tags used throughout: **[primary]** = official GitHub README / repo text read directly in this session; **[search excerpt]** = text quoted from a paper (arXiv/CVF/NeurIPS) as surfaced by web search (arxiv.org, openreview, CVF, huggingface.co were blocked by the proxy, so papers could not be opened directly); **[secondary]** = blog/news/third-party summary; **[recalled]** = from model background knowledge, NOT re-verified this session (treat as needing verification). FLOP savings are labelled "FLOPs"; measured wall-clock is labelled "measured" with hardware where known. Date context: today is 2026-10-12.

## Q1. Mixture-of-Depths (MoD) and Mixture-of-Recursions (MoR) as "fewer tokens per pass": routers, capacity, causality, FLOP savings

### Takeaway
MoD and MoR are the trained (pretraining or long continued-training) way to make each block/loop pass touch only a top-k subset of tokens; MoR is literally "MoD applied across the iterations of a shared block", so it is the most direct token-sparsity design for looped LMs (up to ~2x inference throughput claimed). Both need extra machinery for autoregressive decoding because expert-choice top-k over a sequence is non-causal; neither is training-free.

### Cited Findings
- MoD (Raposo et al., DeepMind, Apr 2024, arXiv 2404.02258): top-k over a sequence is non-causal — a token's selection depends on routing weights of later tokens, unavailable during autoregressive decoding. — [search excerpt](https://arxiv.org/pdf/2404.02258)
- MoD fix #1: auxiliary binary cross-entropy loss on the router logits with top-k membership as target; reported to affect the primary LM objective by ~0.2–0.3% but allows autoregressive sampling. Fix #2: a small auxiliary MLP predictor (stop-gradient on router inputs) predicts top-k membership; leaves LM objective unaffected, does not significantly impact step speed, reaches ~99% accuracy quickly. — [search excerpt](https://arxiv.org/pdf/2404.02258)
- MoD best configuration (secondary): route every other block with top-k = 256 of 2048, i.e. 12.5% capacity — only 12.5% of tokens go through attention+MLP in routed blocks, the rest ride the residual. — [secondary, aiwiki](https://aiwiki.ai/wiki/mixture_of_depths/raw); [secondary, HackerNoon](https://hackernoon.com/what-if-ai-could-skip-the-boring-parts-google-researchers-just-made-it-happen)
- MoD speed: a 220M MoD model slightly beats the isoFLOP-optimal 220M baseline while being >60% faster to step (figure caption says 66% for one variant); on equal hardware total training wall-clock is about the same (gain is per-step / per-forward-pass). — [secondary, HackerNoon summary](https://hackernoon.com/what-if-ai-could-skip-the-boring-parts-google-researchers-just-made-it-happen)
- MoD abstract wording (models "require a fraction of the FLOPs per forward pass, and can be upwards of 50% faster to step during post-training sampling"). — [recalled; abstract at arXiv 2404.02258](https://arxiv.org/pdf/2404.02258); a curator page paraphrases "up to 50% faster" inference — [secondary, DAIR.AI](https://academy.dair.ai/papers/mixture-of-depths). Back-of-envelope (not a paper result): C=0.125 on alternating blocks ≈ 56% of dense compute/token (~1.8x fewer FLOPs). — [secondary, aiwiki](https://aiwiki.ai/wiki/mixture_of_depths/raw)
- MoMa (Meta, 2024) reuses MoD-style auxiliary routers at inference that predict selection "solely based on its hidden representation". — [search excerpt](https://arxiv.org/pdf/2407.21770)
- MoR (Bae et al., Jul 2025, NeurIPS 2025, arXiv 2507.10524): lightweight routers trained end-to-end assign each token a recursion depth through a shared block stack; two router types: expert-choice (each recursion step picks its top-k tokens; scores via sigmoid/tanh with a per-step percentile threshold) and token-choice (depth assigned up front). — [search excerpt](https://arxiv.org/pdf/2507.10524); code has `expert_choice_router.py` and `token_choice_router.py`; "For expert-choice, we can avoid variable-length complexities since all samples have the same length" — [primary, GitHub](https://github.com/raymin0223/mixture_of_recursions)
- MoR causality: expert-choice handles inference causality via auxiliary loss terms / auxiliary router; token-choice is inherently causal but suffers load imbalance across depths. — [secondary, VentureBeat](https://venturebeat.com/ai/mixture-of-recursions-delivers-2x-faster-inference-heres-how-to-implement-it); MoR reports some auxiliary-router variants have dead-token ratios as high as 66.7% (router always picks the same positions). — [search excerpt](https://arxiv.org/pdf/2507.10524)
- MoR KV handling: "recursion-wise KV caching" stores KV only for tokens active at a given recursion (attention runs only among active tokens); a "recursive KV sharing" variant reuses the first recursion's KV to cut memory further. — [search excerpt](https://arxiv.org/html/2507.10524v3); README frames this as solving the "missing KV cache problem" of early-exit — [primary](https://github.com/raymin0223/mixture_of_recursions)
- MoR results: 135M–1.7B params, 2e18–16.5e18 training FLOPs; slightly worse than vanilla at 135M, matches/exceeds vanilla at ≥360M; at 16.5e18 FLOPs uses ~50% fewer params with lower val loss; MoR-4 (4 recursions) up to 2.06x inference throughput vs vanilla using continuous depth-wise batching + early exit (measured at 360M scale per a summary). — [secondary, VentureBeat](https://venturebeat.com/ai/mixture-of-recursions-delivers-2x-faster-inference-heres-how-to-implement-it); README: "up to 2× greater inference throughput compared to standard transformers at similar accuracy"; released 360M Vanilla/Recursive/MoR checkpoints; Llama-based; FineWeb-Edu — [primary](https://github.com/raymin0223/mixture_of_recursions)
- T-LoopFormer (Sep 2026, arXiv 2609.15160): token-level elastic-depth looped transformer; token-choice router with threshold 0.5; separate KV cache per loop; FLOP-matched against a 24-layer ~1B non-looped baseline; FineWeb-Edu 25B tokens; baselines Base-Loop, TMLT and early-exit variants. Numeric results not retrieved. — [search excerpt](https://arxiv.org/pdf/2609.15160)
- Inner Thinking Transformer (ITT, ACL 2025, arXiv 2502.13842): "Adaptive Token Routing" allocates extra shared-layer "thinking steps" to hard tokens plus residual thinking connections; arXiv version: 162M ITT reaches ~96.5% of a 466M Transformer using 43.2% less training data. — [search excerpt](https://arxiv.org/html/2502.13842v2)

### Inferences
- In a looped model, expert-choice MoR naturally yields a nested, shrinking token set per loop (loop r+1 picks from survivors of loop r), so per-pass cost falls with each loop; with capacities like (100%, 50%, 25%) over 3 loops the shared block's total token-passes drop to ~58% of dense (simple arithmetic, ignoring router and attention-length effects).
- For the user's distilled students: MoD/MoR routers must be learned; a plausible route is to add routers during distillation from the full teacher (teacher gives per-token targets), but no source found that does MoR-style routing post-hoc on an already-trained looped model without training.
- Expert-choice with a fixed k gives static tensor shapes (good for TensorRT/Core ML/WebGPU); token-choice / threshold routers give data-dependent shapes.

### Gaps
- Primary MoD/MoR tables (exact capacity sweeps, per-step decode latency) could not be opened (arxiv blocked); the "50% faster sampling" phrase is recalled, not verified this session.
- No MoD/MoR results found for ViTs or per-frame vision models, and none measured on phones/Jetson.
- T-LoopFormer's quantitative results not retrieved.

## Q2. ViT token reduction (ToMe, DynamicViT, EViT, A-ViT, ATS, PiToMe, ToFu, etc.): savings, quality cost, training-free vs trained

### Takeaway
Merging-based methods (ToMe, ToFu, PiToMe, DSM) work training-free on pretrained ViTs and give ~1.6–2x measured GPU throughput; quality cost is ~2% on small 224px models but only ~0.3–0.8% on large/high-resolution models. Learned pruning (DynamicViT, EViT, A-ViT, ATS, LTMP) cuts ~30–50% FLOPs at ≤0.5% drop on DeiT-S but needs 1–100 fine-tuning epochs. DINOv2 features are unusually self-similar, so merging hurts them more.

### Cited Findings
- ToMe (Bolya et al., ICLR 2023): bipartite soft matching merges r tokens per block; "can 2× the throughput of state-of-the-art ViT-L @ 512 and ViT-H @ 518 models on images ... with only a 0.2-0.3% accuracy drop"; lightweight and insertable into any standard block. — [search excerpt](https://arxiv.org/pdf/2210.09461). The abstract also claims 2.2x throughput of ViT-L on video and up to 2x faster MAE fine-tuning on video. — [recalled; arXiv 2210.09461](https://arxiv.org/pdf/2210.09461)
- ToMe README (V100, ImageNet-1k, "without having to do additional training"; repo archived Jan 2025) — off-the-shelf timm AugReg: ViT-S/16 81.41→79.30 @ 953→1564 im/s (r=13); ViT-B/16 84.57→82.60 @ 309→511 (r=13); ViT-L/16 85.82→84.26 @ 95→167 (r=7); ViT-L/16@384 86.92→86.14 @ 28→56 (r=23). Off-the-shelf SWAG: ViT-B@384 85.30→84.59 @ 85.7→167.7 (r=45); ViT-L@512 88.06→87.80 @ 12.8→26.3; ViT-H@518 88.55→88.25 @ 4.7→9.8. Off-the-shelf MAE ViT-L: 85.96→84.22 @ 93→183 (r=8). Trained with ToMe: DeiT-S 79.8→79.36 @ 930→1550; DeiT-Ti 71.8→71.27 @ 2558→3980; MAE fine-tuned w/ ToMe: ViT-B 83.62→81.91 @ 309→603 (r=16), ViT-L 85.66→85.09 @ 93→183, ViT-H 86.88→86.46 @ 35→63. — [primary, GitHub](https://github.com/facebookresearch/ToMe)
- ToMe for Stable Diffusion (training-free, SD1.5 512px, RTX 4090, fp16, 50 PLMS steps): 50% merge → 1.87x faster (3.09→1.65 s/im), FID 33.12→33.02, 3.83x less memory; 60% → 2.03x faster, 5.68x less memory. — [primary, GitHub tomesd](https://github.com/dbolya/tomesd)
- ToFu / Token Fusion (Kim et al., Samsung, WACV 2024): pruning in early layers (models sensitive to interpolation), merging later, MLERP merge preserving norms; applicable with or without training. ViT-L r=8 off-the-shelf: ToFu 84.67% @ 181.31 im/s vs ToMe 84.22% @ 182.05; unreduced ViT-L 97.52 im/s (~1.86x). — [search excerpt, CVF/arXiv 2312.01026](https://arxiv.org/pdf/2312.01026)
- PiToMe (NeurIPS 2024): energy-score spectrum-preserving merging; saves 40–60% FLOPs; off-the-shelf 0.5% average drop on ViT-MAE-H (vs 2.6% for BSM baselines); 0.3% drop for CLIP on Flickr30k retrieval (vs 4.5%). — [primary, GitHub](https://github.com/hchautran/PiToMe)
- DSM, Delayed Spatial Merging (training-free, ICML/NeurIPS 2024 workshops): up to 1.8x FLOP reduction and 1.6x throughput at negligible loss. — [search excerpt](https://arxiv.org/pdf/2303.02331)
- DynamicViT (NeurIPS 2021; T-PAMI extension): learned progressive token pruning; ">30% FLOPs, >40% throughput, accuracy drop within 0.5%"; DeiT-S/0.7: 79.32% @ 2.9 GFLOPs; DeiT-B/0.7: 81.43% @ 11.4G; LV-ViT-S/0.7 83.08% @ 4.6G; trained 30 epochs (15 epochs ≈ 0.1% lower). — [primary, GitHub](https://github.com/raoyongming/DynamicViT). Paper: 31–37% FLOPs reduction, 43–54% throughput, −0.2 to −0.5%, RTX 3090 batch 32. — [search excerpt](https://arxiv.org/pdf/2106.02034)
- EViT (ICLR 2022): keeps top-attentive tokens (by CLS attention) and fuses the rest into one token; DeiT-S with fusion: keep 0.9 → 79.8% 4.0 GMACs 3197 im/s; 0.7 → 79.5% 3.0G 4385 im/s; 0.5 → 78.5% 2.3G 5408 im/s (DeiT-S baseline 79.8% / 4.6G). Requires training. — [primary, GitHub](https://github.com/youweiliang/evit)
- A-ViT (NVIDIA, CVPR 2022): per-token adaptive halting (ACT) inside a ViT; A-ViT-T 71.4% @ 0.8 GFLOPs; A-ViT-S 78.8% @ 3.6 GFLOPs; 100-epoch fine-tune from DeiT; README notes "run-time token zipping for inference" is planned but not released (i.e. released code does not physically drop halted tokens). — [primary, GitHub](https://github.com/NVlabs/A-ViT); throughput +62% DeiT-T, +38% DeiT-S — [secondary review](https://liner.com/review/avit-adaptive-tokens-for-efficient-vision-transformer)
- Side-by-side DeiT-S (79.8% / 4.6 GFLOPs baseline) from SViT supplementary: DynamicViT 3.0G 79.3 (−0.5); EViT 3.0G 79.5 (−0.3); A-ViT 3.6G 78.6 (−1.3, 100 epochs); ATS 3.0G 79.7 (−0.1). — [search excerpt, WACV 2024 supp](https://openaccess.thecvf.com/content/WACV2024/supplemental/Liu_Revisiting_Token_Pruning_WACV_2024_supplemental.pdf)
- LTMP (TMLR 2023): learned-threshold merge+prune, SOTA accuracy across reduction rates "while requiring only a single fine-tuning epoch". — [primary, GitHub](https://github.com/Mxbonn/ltmp)
- "Which Tokens to Use?" (Haurum et al., ICCV 2023): first systematic comparison of 10 token-reduction methods (incl. Top-K, EViT, DynamicViT, ATS, ToMe, DPC-KNN, SiT, PatchMerger, Sinkhorn) on 4 datasets in one codebase, reducing at blocks 4/7/10. — [primary, GitHub](https://github.com/JoakimHaurum/TokenReduction)
- Dense prediction, training-free: Token Adapter (ECCV 2024) removes rows/columns of tokens without retraining, ~41% FPS gain on Segmenter ADE20K at no loss; Segformer++ up to 4x speedup without retraining at high resolution; MPM (Apr 2026, mutual-pair merging, restores token grid before decoder) up to 60% lower per-image latency on Raspberry Pi 5 with ViT-Tiny, up to 20% H100 throughput with FlashAttention-2, <3% mIoU drop, and notes merge-map overhead can erase gains on modern accelerators. — [search excerpt](https://arxiv.org/pdf/2604.05718); [ECCV 2024 listing](https://mlanthology.org/eccv/2024/su2024eccv-removing); [Segformer++](https://arxiv.org/html/2405.14467v1)
- ALGM (CVPR 2024) for Segmenter: local 2x2 window merging at layer 1 then global merging at layer 5, cosine threshold ~0.88; trained/fine-tuned config. — [primary, GitHub](https://github.com/tue-mps/algm-segmenter)
- DINOv2: in a segmentation study (G2TM, Sep 2026), DINOv2 tokens are so mutually similar that merging degrades accuracy more sharply than for AugReg-pretrained ViTs (while giving larger efficiency gains). — [search excerpt](https://arxiv.org/pdf/2609.18279)
- Depth (DPT heads): importance-guided pruning removed ~12% of backbone FLOPs but wall-clock gain appeared only at 448x448 (1.12x); a two-stage schedule beat ToMe-style scoring on NYU-Depth-V2. — [search excerpt](https://arxiv.org/pdf/2609.27988)

### Inferences
- Cross-check: ToFu's ViT-L r=8 ToMe number (84.22% @ ~182 im/s) matches the ToMe README's off-the-shelf MAE ViT-L row (85.96 → 84.22 @ 183), so training-free ~1.9x on ViT-L costs ~1.3–1.7 points with ToMe and ~1.3 with ToFu.
- For a looped encoder distilled from a teacher, the learned-pruning methods (EViT/DynamicViT keep-rate schedules) can be folded into the distillation run at little extra cost; EViT's keep-rate design (fixed count per stage) gives static shapes.
- For DINOv2-derived students, expect merging to be less forgiving than ImageNet ViT numbers suggest; prefer pruning-early / merging-late hybrids (ToFu) or learned schedules, and validate on the dense task.

### Gaps
- ATS's "off-the-shelf without fine-tuning" claim and exact numbers were not retrieved (only the trained DeiT-S row).
- No primary DINOv2 classification/depth tables with ToMe; no Depth Anything + token-merging paper found.
- ALGM numeric results not retrieved.

## Q3. Progressive token reduction across loop iterations (dropping/merging tokens between passes of shared blocks)

### Takeaway
Yes, as of Sep 2026 there is direct evidence: FlashLoop (training-free, on Ouro looped LMs) shows that tokens still changing in later loops form a nested, shrinking subset, and updates only 25% then 10% of tokens in loops 3–4 for "lossless" accuracy, 43% fewer prefill FLOPs and up to 1.64x end-to-end speedup. Trained counterparts are MoR (expert-choice nested top-k per recursion), T-LoopFormer and ITT; A-ViT is the ViT analogue (per-token halting). No paper found doing this for a looped ViT.

### Cited Findings
- FlashLoop (Yang et al., arXiv 2609.29812, Sep 2026): training-free; "reduces cross-loop redundancy through token-sparse updates, sparse attention, and KV-residual quantization"; reuse converged token states across loops; loop-aware sparse attention on important keys late in the loop; compress differences between adjacent loops' KV. "Up to 1.64× end-to-end speedup and up to 6× KV-cache memory reduction." Ouro-2.6B R4: memory 16.9 → 6.9 GiB; 8K prefill 214.4 → 121.8 TFLOPs. Defaults: 4 loops, "dense loops 1–2, 25%/10% token retention in loops 3–4, 10% key retention for sparse late-loop decode, 4-bit K/V with group size 64, and a 64-token BF16 residual tail". — [primary, GitHub](https://github.com/Superone77/FlashLoop)
- FlashLoop motivation: high-change tokens become rarer in later loops, and tokens active in a later loop transition are largely a subset of those active in the preceding one; accuracy reported lossless. — [search excerpt](https://arxiv.org/html/2609.29812v1)
- FlashLoop SGLang integration is a draft PR (#41485) with prefill fractions [0.25, 0.1], decode fraction 0.1, four-loop Ouro, INT4 anchor + packed residual KV; it makes no performance claims and its test runs were failing at time of reading. — [primary, GitHub PR](https://github.com/sgl-project/sglang/pull/41485)
- MoR expert-choice: each recursion step selects top-k tokens to continue, so active sets shrink with depth; recursion-wise KV caching keeps KV only for active tokens. — [search excerpt](https://arxiv.org/pdf/2507.10524)
- T-LoopFormer (Sep 2026): each token chooses its number of loop iterations from its hidden state (token-choice router, threshold 0.5), with a per-loop KV cache. — [search excerpt](https://arxiv.org/pdf/2609.15160)
- A-ViT: per-token halting (ACT) — tokens stop being processed at learned depths; 100 epochs fine-tuning; inference "token zipping" not released. — [primary, GitHub](https://github.com/NVlabs/A-ViT)
- LoopCD (Apple, arXiv 2610.02185, Oct 2026) — not token sparsity, but shows halving loops can match full depth, cutting forward FLOPs 22.5–48.2% (pass-count reduction; adjacent slice). — [search excerpt via papers.cool](https://papers.cool/arxiv/2610.02185)

### Inferences
- FlashLoop's recipe maps directly onto the user's A→B→A→B→A→B models: run loop 1 densely, then in later loops update only tokens whose hidden-state delta exceeds a threshold or a top-k fraction, reusing frozen states (and cached K/V) for the rest. For ViTs (bidirectional attention, no KV cache), frozen tokens still need to provide K/V to active tokens: cache their K/V from the last loop in which they were updated (FlashLoop does this for LMs).
- Token merging between loops (coarse token set for later passes) is the ViT-native variant: merge after loop 1, run later loops on fewer tokens, unmerge before the dense head (as ToMe-SD/MPM do). Because weights are shared across loops, nothing about the weights blocks this; the open question is quality without training, which FlashLoop's "lossless" result suggests is favorable for update-skipping but has not been shown for merging in vision.
- Rough FLOP arithmetic for a 3-loop student with keep rates (1.0, 0.5, 0.25): MLP/QKV cost ~58% of dense; for 6 block passes (A,B ×3) applying FlashLoop-like 25%/10% retention to passes 5–6 alone gives (4 + 0.25 + 0.1)/6 ≈ 72.5% of dense token-wise FLOPs (~27% saving).

### Gaps
- No paper found on token pruning/merging between iterations of a looped or recurrent ViT, or on looped models for detection/segmentation/depth.
- FlashLoop's per-model accuracy tables, decode-only speedups and edge measurements not retrieved; results are authors' own and only on CUDA datacenter GPUs.

## Q4. Video/streaming temporal redundancy: recompute only changed tokens, reuse across frames

### Takeaway
For per-frame vision, temporal reuse is the biggest lever: Eventful Transformers (training-free conversion of many models) give 2–4x compute reduction with minor accuracy loss, MaskVD 3.14x FLOPs / 1.5x measured latency on video detection, RLT +35% throughput training-free at ~0.1% drop, Déjà Vu/ReuseViT 2.64x within 2% error (trained decision layers). Measured wall-clock gains are consistently well below FLOP gains because of gating/gather overhead.

### Cited Findings
- Eventful Transformers (Dutson, Li, Gupta, ICCV 2023): identify tokens that changed significantly over time and re-process only those; 2–4x reduction in computation with minor accuracy loss on ImageNet VID (video detection, ViTDet with ViT-B backbone, mAP@0.5) and EPIC-Kitchens 100 (ViViT action recognition); convertible from existing transformers often without retraining; adaptive runtime control of compute. — [search excerpt](https://arxiv.org/pdf/2308.13494); [MLAnthology](https://mlanthology.org/iccv/2023/dutson2023iccv-eventful)
- Eventful ViTDet example: skipping 66% of non-padded tokens at 672x672 gives >2x savings with a 1.68% accuracy drop. — [search excerpt](https://arxiv.org/pdf/2308.13494)
- Eventful wall-time speedups shown on both CPU and GPU, but implementation uses vanilla PyTorch ops and "is likely sub-optimal"; a fused CUDA kernel for gating is expected to improve speedups. — [search excerpt](https://www.arxiv-vanity.com/papers/2308.13494); MaskVD notes Eventful's token gates and buffers reduce the latency benefit of token reduction. — [search excerpt](https://arxiv.org/pdf/2407.12067)
- Eventful ViViT: the temporal sub-model is fine-tuned on outputs of the Eventful spatial model because it is sensitive to the changed temporal pattern. — [search excerpt, ICCV supp](https://openaccess.thecvf.com/content/ICCV2023/supplemental/Dutson_Eventful_Transformers_Leveraging_ICCV_2023_supplemental.pdf); repo: core logic in `blocks.py`, `modules.py`, `policies.py`; ViViT scripts assume a fine-tuned temporal sub-model. — [primary, GitHub](https://github.com/WISION-Lab/eventful-transformer)
- MaskVD (Sarkar et al., WACV 2025): reuse features from previous frames so ViT backbones skip up to 80% of input regions — 3.14x FLOPs and 1.5x latency improvement; memory and latency 2.3x and 1.14x better than prior SOTA at similar detection performance; one tensor stored per windowed block. Supplement: ~56% regions masked with 0.4% mAP drop (ImageNet-VID subset, 1024x1024); ViT-B 0.805 mAP-50. — [search excerpt](https://arxiv.org/pdf/2407.12067); ~0.9% accuracy decrease — [secondary review](https://themoonlight.io/review/maskvd-region-masking-for-efficient-video-object-detection)
- RLT, Run-Length Tokenization (Choudhury et al., CMU, NeurIPS 2024 spotlight): removes runs of patches repeated over time before the model, replacing each run with one token plus a length encoding; training-free: ~35% higher throughput at ~0.1% accuracy drop; fine-tuning wall-clock −30% at matched accuracy; >100% faster training at 30 FPS; up to 80% fewer tokens on longer videos. — [search excerpt](https://arxiv.org/html/2411.05222); README: Kinetics-400 top-1 unchanged with RLT for ViT-B/L/H (80.9/84.7/86.2). — [primary, GitHub](https://github.com/rccchoudhury/rlt)
- Déjà Vu / ReuseViT (Hwang et al., arXiv 2506.14107, VLDB 2025): ViT reuses computation across neighboring frames via trainable decision layers (token similarity, attention importance, reference type, codec metadata) plus restoration layers; codec-like I/P/B frame ordering; reuse applied to QKV projections and FFN (attention kept); memory-compute compaction needed to turn FLOP savings into GPU speedup; up to 2.64x faster embedding generation within 2% error on three video-language tasks. — [search excerpt / alphaXiv](https://www.alphaxiv.org/overview/2506.14107)
- STTM (ICCV 2025, training-free, video LLMs): quadtree multi-granular spatial merging then directed pairwise temporal merging; ~2x speedup at 0.5% drop with 50% token budget, ~3x at 2% drop with 30% budget; query-agnostic so the video's KV cache is reusable across questions. — [search excerpt](https://papers.cool/arxiv/2507.07990); [primary, GitHub](https://github.com/HYUNJS/STTM)
- Other 2025–2026 video-token methods (mostly video-LLM, not dense per-frame): TimeChat-Online drops 82.8% of streaming video tokens (changed-patch only) with 1.76x latency speedup; PruneVid prunes >80% of visual tokens, −74–80% FLOPs; DyCoke ~1.5x training-free; STC caches ViT features for temporally similar frames and recomputes only dynamic tokens; CodecFlow/CoStream uses codec motion vectors to choose which patches enter the ViT. — [search excerpts](https://arxiv.org/html/2504.17343v1); [PruneVid](https://aclanthology.org/2025.findings-acl.1024.pdf); [DyCoke](https://openaccess.thecvf.com/content/CVPR2025/papers/Tao_DyCoke_Dynamic_Compression_of_Tokens_for_Fast_Video_Large_Language_CVPR_2025_paper.pdf); [STC](https://arxiv.org/html/2512.00891v1); [CodecFlow](https://arxiv.org/html/2604.06036v2)
- VidToMe (CVPR 2024): merges self-attention tokens across frames in diffusion video editing for consistency and lower memory (training-free, ToMe-SD based). — [primary, GitHub](https://github.com/lixirui142/VidToMe)

### Inferences
- Interaction with a looped encoder: Eventful-style reuse needs a reference buffer per *effective* layer (unique block × loop index), not per unique block — the cache for unchanged tokens scales with total passes (e.g. 6 passes for A→B×3), so the memory saving of weight sharing does not carry over to temporal caches. Per-pass state ≈ tokens × d_model × (a few buffers) × number of passes.
- Combining both axes is natural: time-axis gating (only changed tokens enter the frame's loop 1) plus loop-axis gating (FlashLoop-like nested active sets in later loops). Errors from reusing stale per-pass activations accumulate both across frames (Eventful handles this with references updated on change) and across loops; periodic dense "I-frames" (as in Déjà Vu's I/P/B scheduling) bound drift.
- For phones/Jetson, prefer fixed-count (top-r) gating policies over thresholds so per-pass tensor shapes stay static; MaskVD's 3.14x FLOPs → 1.5x latency gap shows ~2x overhead loss is typical without custom kernels.
- For dense outputs (segmentation, depth, pose), reuse is attractive because the head needs every token: unchanged tokens keep their previous per-pass outputs rather than being dropped.

### Gaps
- Eventful's exact GPU/CPU wall-clock numbers and per-budget mAP table were not retrievable (paper pages blocked).
- "CMC" (codec-assisted video transformer acceleration) could not be located by exact-title search; no numbers.
- No temporal-reuse results found for monocular depth or pose ViTs specifically, and none on Jetson/phones.

## Q5. LLM decoding: does token sparsity help batch-1 decode? Where it helps (prefill, KV eviction, sparse attention) and relevance to looped models

### Takeaway
At batch-1 decode each step processes one token, so "fewer tokens per pass" reduces to per-token block/loop skipping (MoD/MoR routing) or to attending fewer cached keys (KV eviction/sparse attention). Token sparsity mainly pays off in prefill/long prompts and in KV memory — and looped LMs multiply KV size by the loop count (Ouro-2.6B 4 loops: 48 GiB KV at 32K vs 4 GiB for LLaMA-3.1-8B), making KV sparsity unusually valuable for them.

### Cited Findings
- Looped-LM prefill/KV cost: Ouro-2.6B with four loops takes 27 s to prefill a 32K prompt vs 3 s for LLaMA-3.1-8B; Ouro's KV cache needs 48 GiB vs 4 GiB. — [search excerpt, FlashLoop](https://arxiv.org/html/2609.29812v1)
- FlashLoop applies 10% key retention for sparse late-loop decode and int4 KV residuals; up to 6x KV memory reduction. — [primary](https://github.com/Superone77/FlashLoop)
- MoR recursive KV sharing reuses first-recursion KV across recursions; recursion-wise caching stores KV only for active tokens. — [search excerpt](https://arxiv.org/html/2507.10524v3)
- MoD decode needs a causal predictor (aux MLP ~99% accurate) since top-k is non-causal; MoD reports faster per-step sampling (see Q1). — [search excerpt](https://arxiv.org/pdf/2404.02258)
- H2O (Heavy-Hitter Oracle, NeurIPS 2023): KV eviction keeping recent + heavy-hitter tokens; with 20% heavy hitters improves throughput up to 29x/29x/3x vs DeepSpeed Zero-Inference / HF Accelerate / FlexGen on OPT-6.7B/30B; at the same batch size, latency up to 1.9x lower. — [primary, GitHub](https://github.com/FMInference/H2O)
- StreamingLLM (attention sinks, ICLR 2024): keep initial sink tokens + recent window; up to 22.2x speedup vs sliding-window recomputation in streaming settings; integrated in TensorRT-LLM and HF; run on iPhone via MLC. Does not extend context. — [primary, GitHub](https://github.com/mit-han-lab/streaming-llm)
- SnapKV (NeurIPS 2024): prompt-phase KV compression using an observation window; ~3.6x faster generation and ~8.2x memory efficiency vs baseline at 16K inputs; up to 380K context on one A100-80GB with negligible needle-in-haystack drop. — [search excerpt](https://proceedings.neurips.cc/paper_files/paper/2024/hash/28ab418242603e0f7323e54185d19bde-Abstract.html)
- Prompt compression: LLMLingua up to 20x prompt compression with minimal loss; LongLLMLingua +21.4% RAG with 1/4 tokens; LLMLingua-2 3–6x faster than LLMLingua; MInference up to 10x prefill latency reduction at 1M tokens on A100 (sparse attention). — [primary, GitHub](https://github.com/microsoft/LLMLingua)

### Inferences
- Batch-1 decode on phones/browsers/Jetson is weight-bandwidth-bound for dense models; looping already shares weights (better cache reuse), so per-token routing (MoR-style "fewer loops for easy tokens") saves real compute per step, whereas KV eviction mostly saves attention reads, which dominate only at long contexts.
- All KV methods (H2O, SnapKV, StreamingLLM, prompt compression) apply to looped LMs unchanged in principle, but cache size and eviction policy must be decided per loop (each loop has its own K/V unless KV sharing is used); FlashLoop's cross-loop KV residual quantization is loop-specific and has no non-looped analogue.
- Prompt compression (LLMLingua) is model-agnostic and composes with looping trivially since it shrinks input before the model.

### Gaps
- No measured batch-1 decode latency for MoD/MoR on edge hardware found.
- H2O/SnapKV/StreamingLLM have not been evaluated on looped LMs in sources found (beyond FlashLoop's own loop-aware sparse attention).

## Q6. Realistic savings at <1% quality loss, and what is measured on Jetson Orin / mobile

### Takeaway
Realistic <1%-loss budgets: training-free ~1.6–2x GPU throughput only on large or high-resolution ViTs (small 224px ViTs lose ~2% at 1.65x); with fine-tuning, ~30–40% fewer FLOPs / ~40–50% more throughput at ≤0.5% on DeiT-S; for video, 1.35–2x (RLT, STTM at 50% budget, MaskVD at 56% masking). On edge at batch 1 the picture is much worse: several token-reduction methods *increase* latency 2–30% on Jetson TX2/AGX Orin because of overhead and non-linear latency-vs-tokens curves; measure on device.

### Cited Findings
- Eliopoulos et al., "Pruning One More Token is Enough" (WACV 2025, arXiv 2407.05941): edge devices NVIDIA TX2 and AGX Orin (plus A100); latency vs workload is non-linear, so token reductions that don't cross latency steps don't help. Other methods "may increase latency by 2-30% while we reduce latency by 9-26%" (an earlier version: single-batch, others +18.6–30.3%, theirs −9%); at similar latency (within 5.2%) theirs reaches 78.6–84.5% ImageNet-1K vs ToMe 45.8–85.4%; training-free schedule. — [search excerpt](https://arxiv.org/pdf/2407.05941)
- HEART-ViT (arXiv 2512.20120, Dec 2025): token + head pruning with fine-tuning; on Jetson AGX Orin DeiT-B/16 and ViT-B/16 (ImageNet-100) baseline ~23 ms → ~13.6–18.7 ms (≈19–43% latency improvement), 35–43% at 40–60% pruning ratios. — [search excerpt](https://arxiv.org/pdf/2512.20120)
- SPViT (ECCV 2022): latency-aware learned soft token pruning (pruned tokens merged into a package token); on a mobile device reduces DeiT-T latency to 26 ms (26–41% better than prior work) with 0.25–4% higher top-1. — [search excerpt](https://www.ecva.net/papers/eccv_2022/papers_ECCV/html/6265_ECCV_2022_paper.php)
- MPM (Apr 2026, training-free): up to 60% lower latency on Raspberry Pi 5 (ViT-Tiny, ADE20K), <3% mIoU drop; only up to 20% on H100. — [search excerpt](https://arxiv.org/pdf/2604.05718)
- JetViT (CVPR 2026 Findings; post-training attention search, not token reduction): Depth Anything V2-L at 2K on Jetson GB10 803 → 529 ms; up to 2.4x on RTX 3090/Jetson GB10. — [search excerpt](https://arxiv.org/pdf/2605.26636)
- Depth pruning on DPT: 12% FLOPs removed → only 1.12x wall-clock and only at 448x448. — [search excerpt](https://arxiv.org/pdf/2609.27988)
- <1% loss datapoints (datacenter GPUs): ToMe off-the-shelf SWAG ViT-L@512 −0.26 at 2.05x, ViT-H@518 −0.30 at 2.09x, ViT-L@384 (timm) −0.78 at 2.0x; DeiT-S trained with ToMe −0.44 at 1.67x; ViT-S/B@224 off-the-shelf ~−2 at ~1.65x (V100). — [primary, ToMe README](https://github.com/facebookresearch/ToMe); EViT DeiT-S keep 0.7 −0.3 at 3.0 vs 4.6 GMACs; DynamicViT −0.2 to −0.5 at 31–37% fewer FLOPs, +43–54% throughput (RTX 3090, batch 32). — [primary, EViT](https://github.com/youweiliang/evit); [search excerpt, DynamicViT](https://arxiv.org/pdf/2106.02034)
- Video <1%: RLT +35% throughput at ~0.1% (training-free); STTM ~2x at 0.5%; MaskVD 56% masking at 0.4% mAP drop; Eventful >2x at 1.68% (above 1%). — [RLT](https://arxiv.org/html/2411.05222); [STTM](https://papers.cool/arxiv/2507.07990); [MaskVD supp](https://openaccess.thecvf.com/content/WACV2025/supplemental/Sarkar_MaskVD_Region_Masking_WACV_2025_supplemental.pdf); [Eventful](https://arxiv.org/pdf/2308.13494)
- Looped LM: FlashLoop "lossless" with 1.64x end-to-end and 43% fewer 8K-prefill FLOPs (datacenter CUDA). — [primary](https://github.com/Superone77/FlashLoop)

### Inferences
- On batch-1 edge GPUs (Jetson) the GPU is often under-occupied at ViT-S/B token counts, so cutting tokens below the occupancy knee gives little; savings appear at high resolution (dense tasks, 518–1024px) where token counts are in the thousands — which is the user's per-frame vision regime, so token methods are more promising there than for small classifiers.
- Budget planning: measured speedup can be as low as ~half the FLOP speedup for gather/scatter-based methods without custom kernels (MaskVD 3.14x FLOPs → 1.5x latency), can vanish at small input sizes (DPT pruning helped only at 448x448), and is hardware-dependent (MPM up to 60% on Raspberry Pi 5 CPU vs up to 20% on H100); verify static-shape export (TensorRT, Core ML, WebGPU) since data-dependent token counts may force dynamic shapes or padding.
- Phones/browsers (CPU/NPU/WebGPU) tend to be more compute-bound than big GPUs at batch 1 (cf. MPM's larger gain on Raspberry Pi 5), so FLOP reductions may translate better there than on Jetson GPU — unverified for NPUs.

### Gaps
- No measured ToMe/EViT/Eventful numbers on Jetson Orin found other than the Eliopoulos aggregate and HEART-ViT; exact Orin device tables not retrievable.
- No browser (WebGPU/WASM) or phone-NPU measurements of token reduction found.
- No measurements of any token-sparsity method on a looped vision model, on any hardware.
